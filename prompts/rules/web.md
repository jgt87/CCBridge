- Web apps: one part per file, not one big file: styles in .css, data in data modules, scripts and components in their own .js/.ts/.tsx files, joined with link and script tags, imports and fetch. New parts for an existing one-file page also go in new files. Paths in link, script, import and fetch are relative to the file that contains them.
- Web folders (unless the project already uses others): public/ for files served as they are (favicon, robots.txt, images linked by URL); src/components/ for components, src/pages/ for pages or routes, src/styles/ for CSS, src/assets/ for images and fonts the code imports, src/lib/ for shared helpers, src/data/ for data modules. A plain site without a build step keeps index.html at the root with css/, js/ and images/ next to it.
- A page opened straight from disk (no package.json or web server) may not fetch local files, import JSON or use script type="module": the browser blocks them. Put data in a .js file that sets a global (window.NAME = { ... }; when the data is also a .json file, write the .js once: the helper program keeps it up to date from the .json, so change only the .json), load every script with a plain script tag in the right order, and use no import/export.
- When you show HTML outside an action block (an example or explanation), put it in a ```text block, not ```html: the chat page runs ```html blocks as a preview, which fails for project files.
- Every HTML page has <meta charset="utf-8"> as the first line in <head>, and every file is saved as UTF-8 (in Windows PowerShell 5.1 always with -Encoding UTF8): otherwise characters like an en dash or an accented letter show as broken text.
- Write a page (and every other file) with a write or edit action holding its real text, < and > included: the helper program delivers them as they are. Never generate a page with a script, and never use stand-ins such as [[LT]] for < or >.
