POWERSHELL WINDOW APPS
- Build the window with WPF in Windows PowerShell 5.1 (nothing to install): the window in MainWindow.xaml next to the script, the code in the .ps1. Windows Forms only when the person asks for it.
- Use the helpers the helper program writes: styles/kit/wpf/KitWpf.ps1 (read its header for every function). Dot-source it first: . (Join-Path $PSScriptRoot 'styles\kit\wpf\KitWpf.ps1') (the path from the script to the file), then $ui = New-KitWindow -Path (Join-Path $PSScriptRoot 'MainWindow.xaml') gives $ui.Window and every element with an x:Name ($ui.Refresh, $ui.Grid); connect events in PowerShell ($ui.Refresh.Add_Click({ ... })) and end with Show-KitWindow $ui. Never write your own version of what a helper does.
- XAML read by XamlReader takes no x:Class and no event attributes (Click="...", Loaded="..."): name elements with x:Name and connect events in PowerShell.
- What there is, and how: a table of rows (DataGrid; Set-KitGrid, sortable, numbers right-aligned; Set-KitGridFilter for a search box), a chart as a bar list (Set-KitBars into a StackPanel; WPF has no chart control), files and folders (Select-KitFile, Select-KitFolder; Import-KitData for CSV, TSV and JSON; Export-KitCsv), messages and questions (Show-KitMessage), a status line under the actions (Set-KitStatus with ok, warn, error), long work without a frozen window (Start-KitWork with -OnDone and -OnProgress, Send-KitProgress inside; Set-KitBusy meanwhile), keyboard shortcuts (Add-KitShortcut), something every few seconds (New-KitTimer), settings kept between runs (Get-KitSettings, Save-KitSettings), one copy of the app at a time (Use-KitSingleInstance). Layout with Grid, StackPanel and DockPanel; TabControl for pages, Expander for optional parts, DatePicker for dates, ComboBox for a choice, CheckBox and RadioButton, ProgressBar, Menu and ToolBar when the app has many actions, StatusBar at the bottom.
- Alignment: lay the window out with DockPanel (header at the top, status bar at the bottom, the content filling the rest) and Grid; never place controls by coordinates (no Canvas for controls, no large Margin with Left/Top alignment). Mark panels and the helper program writes their layout into the XAML after each step (Orientation, alignment, margins, grid rows and columns: read the file again before you edit those lines), so the window lines up however it is loaded: a StackPanel Tag="row" for controls side by side (left, centred on one line, 8 apart: a search box, a filter, a button), a StackPanel Tag="actions" for the window's buttons (at the right, the main action last), a Grid Tag="form" for labels with their fields (label, field, label, field: the labels in one column, the fields lined up in a second that fills the width). Everything starts at the same left edge: a control with a Width also gets HorizontalAlignment="Left", or WPF centres it. Sizes are uniform: leave out Height on buttons, single-line fields, drop-downs and date pickers (they all get one height), and give a field a Width only from the scale 120 (a number, a date, a short choice), 240 (a name, a search, a choice) or 360 (long text), or let it fill its column (Grid Tag="form", where all fields share one width). Fields above each other have the same width. Keep spacing to 4, 8, 12 or 16. The helper program measures the open window and reports what does not line up.
- The look comes from the UI kit: KitWpf.ps1 loads styles/kit/wpf/KitTheme.xaml (the helper program writes it from the project's colours) before the window, so every control has the kit's look by itself. The main action uses Style="{StaticResource KitPrimaryButton}", a heading KitTitle, small grey text KitMuted, a panel <Border Style="{StaticResource KitPanel}">; brushes such as {StaticResource KitAccent} or KitChart1 when you need a colour. Do not set colours, fonts or corner sizes of your own.
- Every control a person uses has a name for screen readers: visible text, or AutomationProperties.Name="..." on an icon-only button or a field (a Label with Target="{Binding ElementName=Field}" also names it). Click targets are at least 24 x 24; nothing may be cut off at the window's starting size (set a Width and Height that fit, or a MinWidth and MinHeight).
- Find the project folder from the script ($PSScriptRoot), never from the current folder.
- Start: a .cmd next to the script, named like it, with powershell.exe -NoProfile -ExecutionPolicy Bypass -STA -WindowStyle Hidden -File "%~dp0NAME.ps1", so a double click opens the window without a console.
- A test next to the script, NAME.guitest, that the helper program runs after it opened the window: one step per line, click NAME, type NAME = TEXT, select NAME = ITEM, expect NAME = TEXT (the element's text or value contains TEXT; expect TEXT alone: anywhere in the window), wait MS. NAME is an x:Name or the visible text. Cover the main things a person does; never a step that deletes, sends or changes real data.
- When the environment variable STREAMHUB_GUI_TEST is set (Test-KitGuiTest), the helper program is checking the window: open it without doing work at start (no file changes, no web calls), use sample rows where the app would load real data, and never show a message box at start; it closes the window itself.
