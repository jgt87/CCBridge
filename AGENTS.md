# CCBridge - instructions for coding agents

> Product name shown to people: **StreamHub** (UI, messages, README, releases). The code, scripts, data folder (`%LOCALAPPDATA%\CCBridge`), projects folder (`OneDrive\CCBridge`), MCP id (`ccbridge`) and the repository keep the name CCBridge. In visible texts and logs, Microsoft's own reply endpoint (`m365Copilot/StreamHub`) is called the "Copilot stream connection" so the two never get confused.

CCBridge is a zero-install coding harness that uses Microsoft 365 Copilot Chat (in Edge) as its model. It ships two front ends over one engine:
- **Web app**: `ccbridge.ps1` / `start.cmd` serves `ui/` on http://localhost:8765 (projects must be under OneDrive).
- **MCP server**: `mcp/ccbridge-mcp.ps1` (stdio), so MCP clients can offload work to Copilot (any project folder).

Target machines have only what ships with Windows: **Windows PowerShell 5.1 + Edge, nothing installed.** Node is only needed on a dev machine to rebuild the UI.

| `lib/Protocol.psm1` | Parses action blocks (`read glob grep find web write edit run remember todo done`) from replies. The form Copilot is taught: a ```` ```text ```` block (four backticks for write/edit) whose first line is `ACTION NAME [ARG]`; edits use `####### SEARCH` / `####### REPLACE` / `####### END` (old `<<<<<<<` / `=======` / `>>>>>>>` still read; in a block with the new markers only `#######` lines count: `Get-EditMarker -NewOnly`, tests `tests/EditMarkers.Tests.ps1`), because Copilot's page draws any other label (`read`, even `text read`) as a Chart.js chart with "Invalid JSON" on some tenants (`test-tools\render-test.cmd`). Still accepted: the name as the label (```` ```read ````) and a bare name as the first line of a plain block (a shorter list). A run block's command belongs on the line after `ACTION run`; written on the ACTION line itself (`ACTION run powershell.exe ...`) it is taken as the command when nothing follows, and a run block with no command at all is refused by Agent `Invoke-AgentAction` (no approval card for nothing). ## PowerShell 5.1 rules (each of these has bitten this repo)

- Keep `.ps1`/`.psm1` **ASCII-only**; BOM-less files are read as ANSI. Write non-ASCII as `\u` escapes in JS strings or `[char]0x..`.
- An `if` without `else` assigned to a variable yields AutomationNull, which `ConvertTo-Json` writes as `{}`. Assign `$null` explicitly first.
- `return , $array` plus a caller's `@()` nests the array. Return arrays plainly and wrap at the call site.
- `$hashtable + @{...}` throws on duplicate keys; use `Join-Hash` (Agent.psm1).
- The comma binds tighter than `+`: `@($x, $i + 1)` is `($x, $i) + 1`. Write `@($x, ($i + 1))`.
- A `[pscustomobject]` has no `.Count` in 5.1: wrap single results in `@()` before counting.
- `Invoke-RestMethod` emits a JSON array as one object; wrap the call in parentheses before piping.
- 2-D array indexes with commas inside method arguments do not parse; use flat arrays.
- Native-command stderr with `$ErrorActionPreference = 'Stop'` becomes a terminating error; silence via `cmd /c "... >nul 2>&1"`.
- Don't name functions like built-in cmdlets (`Wait-Job`, `New-Job`).
- In strings, `"$name: ..."` parses as a scope-qualified variable; write `"${name}: ..."`.
- Log with `Write-CCBLog info|verbose|trace <component> <message> [data]` (lib/Log.psm1). Each process starts every log file it writes to with `Get-LogHeader` (version and commit from `Initialize-CCBLog -Build (Format-CCBBuild (Get-CCBridgeBuild $root)) -Role`, kept in `$env:CCBRIDGE_LOG_BUILD`/`_ROLE`/`_HEADER` so worker runspaces share it; without -Build, version.txt/commit.txt or dev). Never put prompt/reply text or file contents below `trace`.
- Tests that create a temporary project set `$env:CCBRIDGE_STATE_ROOT` to a temporary folder at the top and delete it at the end (see `tests/Undo.Tests.ps1`): `Get-ProjectStateDir` then keeps their backups and chat history out of `%LOCALAPPDATA%\CCBridge\projects`.
- In the MCP server, stdout is the protocol channel: never let pipeline output or `Write-Host` reach it; log to stderr.

## Copilot Chat quirks the code depends on

- The message box is a **Lexical** editor (`#m365-chat-editor-target-element`): it is re-mounted about 3 times after load (wait until the same element is stable), ignores `execCommand` (clear with Ctrl+A/Backspace key events), and turns `\r` into extra characters (send `\n` only).
- Replies arrive on `substrate.office.com/m365Copilot/Chathub` (SignalR, records separated by `0x1e`); a `type:2` record ends the reply and carries throttling (messages per chat) and metering (daily credits, `OutOfCredits`).
- Copilot's **link/citation filter damages code** in snapshots and the final text (`[name]:`, `[guid]::`, `[x](...)` vanish). The reply is rebuilt from raw `writeAtCursor` chunks (`Add-ReplySnapshot`). Never use the server's final text for code.

## Product rules

- **CCBridge has no language model of its own.** Copilot is the only intelligence; everything CCBridge decides (task kind, which instructions to send, follow-up recaps and re-sends, nudges, when a reply is finished, how an edit is applied) is a fixed, testable rule on text and page state. Never write code that assumes CCBridge understands a request. When Copilot misbehaves, fix it with clearer instructions sent to Copilot or a deterministic rule, and cover the rule with a Pester test.
- Task kind (`Get-TaskKind`, Prompts.psm1): coding words, Microsoft 365 words and project words as before; in a project with code (trait `code` from `Get-ProjectTraits`) a request also counts as coding when it asks for a change (also apply, upgrade), names a part of an app (button, header, page, the UI kit...), reports a problem, asks how/why, or names a project file (`Test-NamesProjectFile`); Microsoft 365 requests stay assistant work. Each turn emits a `kind` event; the app shows how a message was sent and offers "Send again as a coding task" (`/api/chat` `asCoding`, `forceKind = coding`). Tasks from MCP/API are never plain chat (`forceKind = work`). Add misdetected phrases to `tests/Prompts.Tests.ps1`.
- Follow-ups in a work chat (`Get-TurnKind`): a chat-like follow-up inherits the chat's task kind; each follow-up gets the recap in `prompts/reminder.md`; the full instructions are sent again after a turn without actions or after every 5 follow-ups.

- **A look the person asks for wins over the UI kit** (`Test-LookRequest` in Prompts: look words plus a change word, English and Dutch): `prompts/rules/userlook.md` goes with the message in a project with the kit (do exactly what is asked, in the project's own CSS or tokens.css, marked `/* Look asked for: ... */`), the round check passes `-UserLook` to `Find-QualityIssues` so the kit's look checks rest for that turn (`$State.UserLook`), and `rules:uikit` says marked styles stay. Add misdetected phrasings to `tests/KitExtras.Tests.ps1`.
- **Project setup before the first request** (`lib/ProjectSetup.psm1`): how a new project is built (one file, separate files, Copilot decides; live data from a file outside the project) is asked by StreamHub with a fixed rule, saved per project and sent with every task. Copilot never reads or edits the blocks StreamHub writes in one-file pages, and StreamHub only reads a live data file, never writes it. Add misdetected phrasings to `tests/ProjectSetup.Tests.ps1`.
- **Fix attempts go further each time** (`Agent.psm1`): `Submit-IssueFix` carries `origin` (the change set that brought the problems, from `Invoke-IssueCycle -ChangeSet`), `lastChange` (the previous attempt's change set) and `diagnosis` in `issueFix`; `New-FixAttemptMessage`: 1 = `New-FixMessage`; 2 = cause first, `Get-FixEvidence` (ranged reads around each problem, `Format-OpenBlocks` from Lint `Get-OpenBlocks` for bracket problems, `Format-ImportUsers`), `Format-LineChange` (Executor) of the previous attempt, `responseMode = deep`; 3 = `freshChat` (worker sets `NeedNewChat`), the diff from the origin's backup (last good version) to now, the earlier diagnosis. `Get-FixDiagnosis` reads the `Cause:` lines from the attempt's replies (`$State.IssueFixFromSeq`) into the next attempt and the "gave up" note. In the round check, `$errorRounds` sends the same evidence the second time an error key is still there. Default `issues.maxAttempts` 3. Tests: `tests/FixLadder.Tests.ps1`.
- **Checks a session review asked for** (all generic): `Invoke-FinalChecks` (Agent) when a turn that changed files ends without the done step finishing (`$doneFinished`, `$endReason`; not for plan mode, MCP review-by-caller or issue fixes): file checks, page and script check, `Find-UnloadedFiles` (Imports: new script/style files no index entry uses and no project file names; tests, configs, tools, build output, data, kit skipped), event `task-unfinished` (UI `UnfinishedCard`, Continue sends `continueText`). Page errors: rechecks up to `enforcement.errorTries`, then `$pageFinal` reports what is left (`PAGE-ERRORS`, `$ev.pageLeft`); the browser's own `/favicon.ico` request is never a page problem (neither its HTTP status nor a failed load), so Copilot is not sent to add an icon link. `Find-UnlinkedKitTokens` (UiKit) and `Find-UndefinedCssVars` (Lint, in `Get-NewFileIssues`, warning by CheckPolicy pattern) for custom properties; kit file edits are a quality note and `$ev.kitEdits`. `Find-EscapedScriptTags` (Lint) for whole escaped tags in `.js` and inline scripts, repaired by AutoFix. Guardrails `Find-PageCopyScript`. The `dispute` action needs a reason and refuses measurements. Fix cases: `lib/FixCases.psm1` `Write-FixCase` (`.streamhub/FixCases/case-*.md`, newest 200), written by `Invoke-IssueCycle` for tries >= 2 (fixed or gave up; `issueFix.request/problems/history`) and at the end of a turn for error keys seen in 2+ rounds (`$errorFirst`, `$lastErrorKeys`); `tools/collect-diagnostics.ps1` collects them.
